# Промпт для Cursor: автоматизация генерации ADR (n8n + Langflow/LangChain как внутренняя нода)

## Задача

Реализуй в n8n единый end-to-end workflow, который автоматически превращает запись завершённой встречи с заказчиком в структурированный Architecture Decision Record (ADR) и направляет его архитектору на ревью перед публикацией. **n8n выступает единой средой выполнения** — оркестрация, интеграции с внешними системами и AI-логика реализованы в одном workflow, без отдельного внешнего AI-сервиса. Интеллектуальная обработка транскрипта (извлечение требований, ограничений, альтернатив и решений, а также генерация итогового ADR) выполняется через **Langflow/LangChain-ноду, работающую как внутренний компонент n8n workflow**, а не как самостоятельный backend с собственным API. Отдельный runtime для Langflow/LangChain разворачивать не нужно — вся логика встроена в узлы n8n.

Пайплайн должен строго следовать зафиксированной в источнике последовательности этапов (порядок фиксирован, реализацию каждого узла и внутреннюю структуру workflow выбирай сам): **Webhook Trigger → получение записи встречи → Speech-to-Text → препроцессинг/чанкинг транскрипта → сбор дополнительного контекста (Jira/Confluence) → AI-экстракция (Langflow/LangChain) → Aggregate/Reduce → генерация ADR → Validation → Human-in-the-loop review → публикация (Confluence/Notion, Jira, Slack/Teams)**. Внутри каждого этапа ты свободен в выборе конкретных нод n8n, способа передачи данных между ними, структуры sub-workflow и деталей реализации — фиксирован только сам порядок этапов, а не то, как каждый из них устроен внутри.

## Технический контекст

Стек: n8n (единая orchestration/runtime среда), Langflow/LangChain-нода внутри n8n для AI-логики (LLM-вызовы для extraction, aggregation и генерации ADR), Speech-to-Text сервис (Whisper или аналог) для транскрибации записи встречи, Jira API и Confluence API для сбора дополнительного контекста и последующей публикации/связывания ADR, Slack/Teams API для уведомлений, Confluence/Notion как целевая система публикации итогового документа. Опционально — векторное хранилище/RAG для сопоставления с существующими архитектурными стандартами и предыдущими ADR (учитывай эту возможность при проектировании ноды AI-экстракции, но не считай её обязательной для MVP).

Настрой workflow так, чтобы:
- Webhook Trigger принимал событие о завершении встречи (например, от Zoom/Teams) с полями вроде `meeting_id`, `recording_url`, `participants`, `project_id`, `jira_epic_id`;
- узел получения записи и Speech-to-Text сохраняли, где это возможно, `speaker_id` и `timestamps` наряду с текстом реплик;
- препроцессинг включал очистку служебных фрагментов, нормализацию текста и разбиение на chunks при превышении разумного размера транскрипта;
- сбор контекста из Jira/Confluence выполнялся через отдельные интеграционные ноды и агрегировался вместе с чанками транскрипта перед передачей в AI-ноду;
- AI-экстракция была разделена как минимум на четыре логические подзадачи (Requirements, Constraints, Alternatives, Decisions Extraction), чтобы избежать смешивания обсуждавшихся альтернатив с фактически принятыми решениями;
- Aggregate/Reduce выполняла дедупликацию, объединение совпадающих требований, сопоставление альтернатив с решениями и выявление противоречий при работе с несколькими chunk'ами.

Если в проекте уже существуют workflow-файлы, конфигурации credentials для Jira/Confluence/Slack или шаблоны ADR — используй и расширяй их, а не создавай дублирующие сущности; если таких файлов нет, создай структуру workflow (JSON n8n workflow, при необходимости — вспомогательные скрипты/Function-ноды) с нуля.

## Требования, ограничения и обработка неоднозначностей

Промежуточный результат AI-экстракции должен быть валидным JSON вида:

```json
{
  "requirements": [],
  "constraints": [],
  "alternatives": [],
  "decisions": [],
  "open_questions": [],
  "risks": []
}
```

Итоговый ADR должен иметь структуру:

```json
{
  "title": "ADR: <краткое описание решения>",
  "status": "Proposed",
  "context": "...",
  "decision": "...",
  "alternatives": [],
  "consequences": {
    "positive": [],
    "negative": []
  },
  "open_questions": [],
  "risks": [],
  "source_meeting": "meeting-123"
}
```

Узел Validation обязан перед публикацией проверять: заполнено ли поле `decision`, присутствует ли `context`, валиден ли JSON, есть ли противоречащие друг другу решения, достаточно ли данных для формирования полноценного ADR. Если в транскрипте не было явно принятого решения, документ должен получить статус `Needs clarification` вместо автоматической фиксации предполагаемого решения — это критическое требование, не допускай его нарушения.

Обработай следующие edge-кейсы явно: отсутствие явного решения в транскрипте (→ статус `Needs clarification`, публикация не блокируется полностью, но помечается как требующая уточнения), невалидный JSON от AI-ноды (→ retry с уточняющим промптом либо остановка workflow с логированием ошибки и уведомлением ответственного, без падения всего процесса), недоступность Jira/Confluence при сборе контекста (→ workflow должен продолжать выполнение с деградацией — ADR генерируется без части контекста, но с явной пометкой, что контекст неполный, а не падать целиком).

Так как в исходном описании не указаны точные технические детали, зафиксируй следующие предположения и действуй по ним, не останавливаясь на уточнения: формат Webhook-события от Zoom/Teams предполагается как стандартный JSON-payload с полями `meeting_id`, `recording_url`, `participants`, `start_time`, `project_id`, `jira_epic_id` (при необходимости адаптируй под реальный формат Zoom/Teams webhook, если он тебе известен); в качестве Speech-to-Text сервиса предполагается использование Whisper API (или совместимого по контракту сервиса) с выводом текста и, по возможности, диаризацией по спикерам; аутентификация к Jira/Confluence/Slack предполагается через API-токены/OAuth2, хранимые в n8n Credentials (создай соответствующие credential-типы, но не хардкодь секреты в коде workflow); точный шаблон итогового ADR-документа в Confluence/Notion предполагается как страница с секциями Title, Status, Context, Decision, Alternatives, Consequences (Positive/Negative), Open Questions, Risks, Source Meeting — в том порядке и составе, что указан в JSON-структуре выше.

## Критерии готовности

Задача считается выполненной, если: workflow работает end-to-end от Webhook Trigger до публикации в Confluence/Notion, Jira и Slack/Teams без ручного вмешательства, кроме шага human review; все промежуточные и итоговые данные соответствуют указанным JSON-структурам; ADR содержит все обязательные секции; узел Validation корректно присваивает статус `Needs clarification` при отсутствии явного решения и блокирует/помечает публикацию при невалидном JSON или противоречивых решениях; шаг Human-in-the-loop review (Approve/Reject/Request changes) встроен в поток строго до финальной публикации и не может быть обойдён; указанные edge-кейсы обработаны без падения всего workflow.
